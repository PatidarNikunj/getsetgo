# Research: 001-oauth-login

Each entry: **Decision**, **Rationale**, **Alternatives considered**. The user picked D2; the others
follow the tech notes and the constitution.

## D1. OAuth client library

- **Decision**:
  - `arctic` 3.7 (oslo project, ESM, depends only on `@oslojs/*`).
  - Google: `arctic.Google` (PKCE built in).
  - GitHub: arctic's generic `OAuth2Client.createAuthorizationURLWithPKCE` (`CodeChallengeMethod.S256`)
    with GitHub's endpoints, because `arctic.GitHub` has no PKCE parameter and GitHub supports PKCE.
  - `generateState()` and `generateCodeVerifier()` from arctic.
- **Rationale**: small, readable, current (released 2026-07). Every protocol step stays visible in
  our code, which suits a learning repo. No session middleware is forced on us.
- **Alternatives**:
  - `openid-client` 6.9: great for OIDC discovery, but GitHub isn't OIDC, so we'd need two code paths.
  - Passport: session-oriented and callback-style, and harder to fit a custom test provider and our
    own cookie and session model.
  - The user didn't pick in the question dialog, so the recommended option was used; easy to revisit
    before implementation.

## D2. AI transcripts contain note text (user decision)

- **Decision**: `apps/ai` stops storing note title, content and summary text in Mongo
  `transcripts`.
  - It keeps `run_id`, `agent`, `model`, `input_sizes` (`title_chars`, `content_chars`),
    `output_sizes` and status.
  - On startup, an idempotent purge removes the text fields from existing transcripts with
    `$unset input.title input.content output.summary`.
- **Rationale**: account and note deletion (FR-018, FR-019) then leave no copies behind, without a
  new api→ai deletion call.
- **Alternatives**:
  - Delete by note id: an extra internal endpoint and cross-service consistency.
  - 30-day TTL: text lingers.
  - Leave as is: breaks erasure.

## D3. Session model

- **Decision**:
  - A `Session` row per signed-in browser, and a chain of `RefreshToken` rows (the "family") per session.
  - The refresh token is 32 random bytes (base64url). Only `sha256(token)` is stored.
  - Each `/auth/refresh` marks the presented token `usedAt`, creates its successor, and extends
    `session.expiresAt = now + 30 days` (sliding, FR-008).
  - Presenting a token that already has `usedAt` revokes the session (`revokedReason = "reuse"`)
    and logs the event (FR-010).
  - **Race window**: if the token was used less than 10 s ago, a second successor is issued instead
    of revoking. That covers parallel tabs and requests renewing at the same moment. The web apps also
    single-flight renewals.
- **Rationale**: standard rotating-refresh-token design, with no Redis dependency for correctness.
  SHA-256 is enough for 256-bit random tokens (no slow hash needed).
- **Alternatives**:
  - Refresh tokens as JWTs: they can't be revoked without state anyway.
  - Redis-only sessions: Upstash's free tier and its eviction make that riskier than Postgres.
  - No grace window: false "stolen session" sign-outs with multiple tabs.

## D4. Access credential

- **Decision**:
  - A JWT signed with HS256 via `jose`, using the secret `AUTH_JWT_SECRET` (≥ 32 chars, generated by
    `setup-env.mjs` and by Render).
  - Claims: `sub` (user id), `sid` (session id), `iss=getsetgo-api`, `aud=getsetgo-web`, `exp`
    15 min from issue.
  - Verified statelessly by the global guard. "Sign out everywhere" and allowlist removal take
    effect at the next renewal, at most 15 min later, as the spec allows (US2-5, FR-020).
  - Account deletion is effective immediately for data: the owner's rows are gone, and a mutation
    whose owner no longer exists gets `UNAUTHENTICATED`.
- **Rationale**: no database read per request. HS256 fits because only the API issues and verifies
  tokens.
- **Alternatives**:
  - RS256/EdDSA: only useful when third parties verify.
  - A Redis denylist for instant revocation: more moving parts than the spec needs.

## D5. Cookies

| Cookie             | Content                                | Attributes                               | Lifetime         |
| ------------------ | -------------------------------------- | ---------------------------------------- | ---------------- |
| `__Host-gsg_at`    | access JWT                             | `HttpOnly; Secure; SameSite=Lax; Path=/` | 15 min           |
| `__Host-gsg_rt`    | refresh token                          | `HttpOnly; Secure; SameSite=Lax; Path=/` | 30 days, sliding |
| `__Host-gsg_oauth` | `state` only (verifier stays in Redis) | `HttpOnly; Secure; SameSite=Lax; Path=/` | 10 min           |

- **How the cookies stay first-party**:
  - The API sets them on responses to `/api/auth/*` and `/api/graphql`, which reach the browser
    through the web app's Next rewrite.
  - So they're first-party to that web app. Each web app has its own sessions, as the spec assumes.
  - `__Host-` forbids `Domain` and requires `Secure`.
  - Browsers treat `http://localhost` as a secure context, so the same names work in development and
    in Playwright (Chromium).
- **Why `Path=/` for the refresh cookie**:
  - Each web app's `proxy.ts` renews sessions server-side on page loads, so it needs the refresh
    cookie on page requests.
  - The token never leaves the server side: it goes browser → Next server → API.
- **Alternatives**:
  - Refresh cookie `Path=/api/auth`: then server-side renewal on navigation is impossible, and the
    first page load after 15 min would flash the sign-in redirect.
  - `SameSite=Strict`: it breaks the provider's redirect back to the callback (cross-site top-level
    navigation), and the first page load after following a link from email.

## D6. OAuth through the same-origin proxy

- **Decision**:
  - Each web app adds the rewrite `/api/auth/:path*` → `${API_URL}/auth/:path*`.
  - The provider `redirect_uri` is `<web origin>/api/auth/<provider>/callback`. Each web app's origin
    is registered at Google and GitHub (two callback URLs per environment; GitHub OAuth apps allow
    only one callback URL per app, so we use **one GitHub OAuth app per web app**).
  - The API derives the web origin from the request's `Origin` header on POST `/start`, validated
    against `CORS_ORIGINS`. It stores that origin in the pending sign-in and uses it to build the
    `redirect_uri` for both the authorization URL and the code exchange.
  - Redirects back to the web app use **relative** `Location` headers (`/`, `/sign-in?error=…`),
    which the browser resolves against the web origin.
  - Next's external rewrites proxy without following redirects and pass `Set-Cookie` through. That
    gets verified in the first implementation task, with a fallback to absolute URLs built from the
    stored origin.
- **Rationale**:
  - Cookies are first-party and there are no cross-site requests (FR-024).
  - Sign-in started in one app completes in that app.
- **Alternatives**: the callback on the API's own domain plus a token hand-off; that puts a token in
  the URL or needs a third-party cookie.

## D7. Pending sign-in and replay protection

- **Decision**:
  - `POST /auth/:provider/start` creates `state` and `codeVerifier`.
  - It stores `{provider, codeVerifier, webOrigin, returnTo}` in Redis under `oauth:pending:<state>`
    with a 600 s TTL, sets `__Host-gsg_oauth=<state>`, and answers 303 to the provider.
  - The callback requires `query.state === cookie state`, then runs `GETDEL` on the Redis key (single
    use, FR-004), clears the cookie and exchanges the code with the verifier.
- **Rationale**: browser binding (cookie) plus single use (GETDEL) plus PKCE.
- **Alternatives**:
  - A signed cookie holding the verifier: not single use without server state.
  - Postgres: overkill for 10-minute data.

## D8. Provider identity and allowlist

- **Google**:
  - Verify the `id_token` with `jose.jwtVerify` against `createRemoteJWKSet(https://www.googleapis.com/oauth2/v3/certs)`,
    with `iss ∈ {https://accounts.google.com, accounts.google.com}` and `aud = GOOGLE_CLIENT_ID`.
  - Identity: `sub`, `email`, `email_verified`, `name`, `picture`.
  - Scopes: `openid email profile`.
- **GitHub**:
  - `GET https://api.github.com/user` gives the stable numeric `id`, plus `login`, `name` and
    `avatar_url`.
  - `GET /user/emails` gives the primary **verified** email, if any.
  - Scopes: `read:user user:email`.
  - Requests send `User-Agent: getsetgo` and an explicit `Accept`.
- **Allowlist (`AUTH_ALLOWLIST`)**:
  - Comma-separated, case-insensitive entries:
    - `alice@example.com`: matches a verified email from any provider.
    - `github:octocat`: matches a GitHub login.
    - `test:<login>` or `test:<prefix>*`: test provider only. The wildcard is accepted only for
      `test:` entries.
  - Checked at sign-in and at every renewal, using the identity stored at the last sign-in. Removal
    takes effect within 15 min (FR-020).
  - Allowlist failures redirect with `error=invite_only` and create no rows.
- **Rationale**: matches the clarifications (verified emails only, no merging, provider usernames).

## D9. reCAPTCHA v3

- **Decision**:
  - The sign-in page loads `https://www.google.com/recaptcha/api.js?render=<siteKey>` with
    `next/script`, using the request nonce and `strategy="afterInteractive"`.
  - Only the sign-in page loads it, and only when `NEXT_PUBLIC_RECAPTCHA_SITE_KEY` is set.
  - On submit, the provider form calls `grecaptcha.execute(siteKey, {action: "sign_in"})` and puts
    the token in a hidden field.
  - The API calls `https://www.google.com/recaptcha/api/siteverify` (fixed URL, A10) and requires
    `success`, `action === "sign_in"`, `score ≥ RECAPTCHA_MIN_SCORE` (default 0.5) and the expected
    hostname. A low score redirects with `error=bot` and a "try again" message (FR-005).
  - Skipped when `RECAPTCHA_SECRET_KEY` is unset (dev/test).
  - CSP additions come from `recaptchaCspSources()`: `script-src`/`frame-src`
    `https://www.google.com/recaptcha/` and `https://www.gstatic.com/recaptcha/`, plus `connect-src`
    for the same. They're added only when the key is set.
  - The sign-in page shows Google's required reCAPTCHA notice as text (the badge can be hidden).
- **Privacy**: reCAPTCHA is security, not analytics. It runs without the GA consent gate, and the
  privacy note in `docs/observability.md` mentions it.
- **Alternatives**:
  - Cloudflare Turnstile: not in the constitution's stack.
  - Running reCAPTCHA on every page: unnecessary data sharing.

## D10. Web app session handling

- **`proxy.ts`** (both apps), for pages other than `/sign-in`:
  - If neither auth cookie is present → 307 to `/sign-in?returnTo=<path>`.
  - If the access cookie is missing, or expiring within 60 s (decoded, **not trusted**; the API
    verifies) and a refresh cookie exists → `POST ${API_URL}/auth/refresh` server-side with that
    cookie and `Origin` set to the app's own origin.
  - On success, copy the `Set-Cookie` headers to the response, and update the request's cookie header
    so the SSR render uses the new access token. On failure → `/sign-in`.
  - `/sign-in` with a valid session → `/`.
- **SSR data fetches**:
  - `lib/session.server.ts` reads the two auth cookies from `cookies()` and forwards **only those**
    to `API_URL` (TanStack prefetch and Apollo `PreloadQuery`).
  - It also loads `me` for the header.
- **Client**:
  - On a GraphQL `UNAUTHENTICATED` error, call `refreshSession()` (shared, single-flight
    `POST /api/auth/refresh`) and retry once. If the renewal fails, go to `/sign-in`.
  - The unsaved note stays in IndexedDB (existing drafts).
  - web-material: an Apollo `ErrorLink`. web-shadcn: a wrapper around `requestGraphQL` used by
    TanStack query and mutation functions.
- **Sign out**: a native `<form method="post" action="/api/auth/sign-out">`, which works before
  hydration. Then Apollo `clearStore()` / `queryClient.clear()` on the next page load.
- **Back button after sign-out** (US2-4): authenticated pages send `Cache-Control: no-store` (set in
  `proxy.ts` for protected routes), so bfcache and HTTP caches don't show the notes.

## D11. Ownership and the release purge

- **Postgres**:
  - The migration runs `DELETE FROM notes` (all current notes are ownerless, FR-019), then adds
    `owner_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE` and index `(owner_id, created_at)`.
- **Mongo summaries**:
  - New summaries store `ownerId`.
  - At startup, `NotesModule` runs an idempotent `deleteMany({ ownerId: { $exists: false } })`.
    Pre-feature summaries are exactly those without an owner.
- **Redis**:
  - List cache keys become `notes:list:<ownerId>:<limit>:<offset>`.
  - Invalidation is per owner. Old keys expire within the existing TTL (and are unreachable anyway).
- **Account deletion**:
  1. Revoke all sessions.
  2. Delete the user's Mongo summaries (`ownerId`).
  3. Delete the user in Postgres; the cascade removes provider accounts, sessions, tokens and notes.
  4. Invalidate the owner's cache.
  5. Clear the cookies.
  - If a step fails, the mutation errors and is safe to retry.

## D12. Test-only OAuth provider

- **Decision**: an in-process `TestProvider`, registered only when `AUTH_TEST_PROVIDER=enabled` and
  `APP_ENV ∈ {development, test}`.
  - `GET /auth/test/authorize` renders a minimal, script-free, accessible HTML form ("Test identity",
    "Email", "Continue"). It runs under the API's `default-src 'none'` CSP, plus `form-action 'self'`
    for this route.
  - Posting the form creates a one-time code in Redis, bound to the PKCE challenge and `redirect_uri`,
    and 303s to the callback.
  - The token exchange verifies the S256 challenge. So e2e tests exercise state, PKCE, the callback,
    cookies and the allowlist exactly like real providers.
- **Production safety**:
  - The `env.ts` schema refuses `AUTH_TEST_PROVIDER=enabled` with `APP_ENV=production`, so the API
    won't boot.
  - The Dockerfile defaults to `APP_ENV=production`, and `render.yaml` sets it explicitly. Only
    `docker-compose.yml` and local `.env` files set `development`/`test`.
  - A unit test covers the refusal.
- **Alternatives**:
  - `mock-oauth2-server` container: a new container, and Google/GitHub endpoint overrides in config.
  - Minting cookies directly in tests: skips the flow we most need to test.

## D13. Logging and privacy

- **Redaction**:
  - pino-http `serializers.req` strips the query string from `/auth/*` URLs.
  - The Sentry scrubber (`scrubSensitive`) strips `code`, `state` and `error_description` query
    parameters, and still drops cookies.
- **Auth events** (FR-023) are logged with `{ event, userId?, sessionId?, provider, reason? }`:
  - `auth.sign_in.succeeded` / `.failed` (reason: denied, invite_only, state_mismatch, bot,
    provider_error)
  - `auth.sign_out`
  - `auth.sign_out_everywhere`
  - `auth.refresh.reuse_detected`
  - `auth.account.deleted`
- **What is never logged**: emails, tokens or codes.
- **GA**: an optional `sign_in` / `sign_out` event without identifiers. It goes through the existing
  consent-gated Measurement Protocol helper.

## D14. Rate limits

`@nestjs/throttler` named limits per IP, using the existing `TRUST_PROXY_HOPS`:

| Route             | Limit               |
| ----------------- | ------------------- |
| `auth/*/start`    | 10/min              |
| `auth/*/callback` | 20/min              |
| `auth/refresh`    | 60/min              |
| `auth/sign-out`   | 20/min              |
| GraphQL           | unchanged (120/min) |

A blocked start redirects with `error=rate_limited` (FR-006).
